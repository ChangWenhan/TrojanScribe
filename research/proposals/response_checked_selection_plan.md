# 根据实际试答挑选投毒文本：实验分析与改进计划

日期：2026-10-26  
状态：待验证的研究计划。本文没有新增实验结果，新增的挑选步骤还需要实现。

**建议优先研究：生成假资料以后，实际检查它能不能影响回答，再决定写入哪些资料。** 当前方法主要按相关程度和重复程度挑选，不能保证选出的资料最能让模型回答指定错误答案。

本计划希望回答三个问题：

1. 当前方法失败，主要是资料没被查到，还是查到后没有被采信？
2. 根据实际试答挑选，是否比当前挑选方式更有效？
3. 把正确资料一起放进去试答，是否比只看假资料试答更接近最终效果？

改进是否有效，以共同规则下的完整比较为准；目前不能保证超过已有基线。

## 2. 所有实验共同遵守的比较规则

**同一个答题模型、同一批题、同一批原本答对的题，才能公平比较攻击方法。**

| 项目 | 具体要求 |
|---|---|
| 现有 HotpotQA 评估 | 保持共享的 60 道题及其指定错误答案，使用 `--use-shared-targets` |
| 现有 MuSiQue 评估 | 保持清单中的 59 道题及其指定错误答案，使用 `--target-records` 读取原清单 |
| 攻击前答案 | 每个模型、每个数据集确定一份共同来源；保存来源文件和校验值，所有方法复用同一批答对题 |
| 正常资料库 | 各方法从相同的干净资料开始；清除上次投毒和资料整理助手留下的内容 |
| 攻击过程 | 除了本次要研究的挑选步骤，其他设置保持一致 |
| 写入预算 | 先保持每题最多 8 条；记录实际条数、覆盖题数和总长度，缺量也算入整体结果 |
| 模型调用预算 | 记录生成、试答、重新生成分别调用多少次；额外试答的成本不能省略 |
| 模型查询权限 | 事先说明能否询问被攻击模型。允许查询的比较与仅使用另一个模型试答的比较分别报告 |
| 原始结果 | 新实验单独保存，保留现有 `cluster` 等名称和旧结果；新方法不能覆盖旧方法的结果文件 |

注：分阶段运行时，`eval-after` 必须保留上一阶段写入的毒文本，不能在回答前再次清掉。

先保留各基线原有设置的比较；如果要研究预算影响，再增加写入预算或调用预算相同的比较，并说明对基线做了哪些调整。

## 3. 第一步：分析失败原因

**先知道失败在哪里，再决定改哪里。** 不必先跑完整的四模型、双数据集新实验。

先抽查 xlam 和 gpt-oss，分别代表当前较有效与较弱的情况。抽查用于找原因，最终结果仍需报告整批问题。

| 观察到的情况 | 要检查的证据 | 下一步方向 |
|---|---|---|
| 没查到本题的假资料 | 实际搜索返回的文段、所属题目、排序 | 检查文本是否容易被正常问题找到 |
| 查到了假资料，仍回答正确 | 同时出现的正确资料、假资料及最终回答 | 检查假资料与正确资料一起出现时是否有效 |
| 回答错了，但不是指定错误答案 | 候选文本是否自相矛盾、是否清楚表达指定答案 | 检查文本的表达和试答结果 |
| 回答为空或运行失败 | 错误记录、调用次数、上下文长度 | 单独统计，不能当作成功改错 |
| 同时出现正确和错误答案 | 完整回答及最终结论 | 人工检查，避免文字匹配误判 |

这些情况可以同时出现，不必强行把每题只归为一类。汇总时说明各类可以重叠。

需要补充保存实际 `kb_search` 返回的文段编号、文本、来源和顺序。当前答案记录主要保存工具调用参数，单独对原问题做一次检索，不能完全代替模型实际改写问题后的搜索结果。

## 4. 第二步：做四组相互可解释的比较

**四组尽量使用同一批候选文本，让差异主要来自挑选方式。** 候选文本指“先生成、还没决定写入的备选资料”。

| 组别 | 怎么挑 | 要回答什么 |
|---|---|---|
| A：当前方法 | 按当前 `cluster` 的相关程度、重复程度和每种风格保留一条的规则挑选 | 作为共同起点 |
| B：取消固定风格要求 | 保持其他挑选规则，只取消每种风格必须占位置的要求 | 固定风格要求是否限制了效果 |
| C：根据单独试答挑选 | 让固定的检查模型只看候选假资料，再根据回答挑选 | 实际试答是否比仅看文本相关程度更有用 |
| D：根据混合资料试答挑选 | 将候选假资料与固定的正常资料放在一起，检查回答后挑选 | 面对正确资料时的效果，是否更能预测正式攻击结果 |

现有 `cluster_greedy` 已取消固定风格要求，可作为 B 的实现参考；新的严格比较应保存并复用同一批候选，而非直接把不同轮生成结果的差距全部归因于挑选方式。

### C、D 的试答怎样进行

1. 候选生成后，检查是否非空、是否包含指定错误答案、是否满足长度限制。
2. 对每条候选做固定次数的试答，保存完整输入和回答。
3. D 组使用从干净资料库预先取得的同一组正常资料，包含正确资料的条件单独说明；各候选看到相同的正常资料和顺序规则。
4. 组合检查使用固定搜索步骤和调用上限。例如每轮加入一条候选，比较剩余候选带来的回答变化，直到达到写入上限。
5. 对 C、D 尽量使用相同的候选集合、搜索步骤和试答次数，区别主要放在是否加入正常资料。
6. 最后才把选出的资料写入资料库，通过原来的完整问答流程评估，不能拿试答成绩代替正式攻击成绩。

优先奖励“回答出现指定错误答案，而且不再被判为正确”的情况；空答案、崩溃单独记。评分规则在运行前确定，对所有候选使用相同规则。

固定资料下的试答与真实搜索仍可能不同，因此还需要检查：挑出的资料实际是否被查到，实际回答是否与试答预测一致。

### 失败或没有提升时怎样解释

- B 比 A 好：提示固定保留各种风格可能带来损失，需要重复确认。
- C 比 A 好：支持根据实际回答挑选的价值。
- D 比 C 好：支持把正常资料一起加入检查的价值。
- C、D 试答很好，正式攻击没有改善：检查模型、资料顺序或实际检索结果与试答不一致。
- 各组差不多：当前瓶颈可能不在挑选方式，应回到失败分析，而不是继续堆挑选规则。

单条资料的试答验证在现有 PoisonedRAG、CorruptRAG-AK 中已经存在。因此，增加 C 本身不足以宣称新的研究贡献；D 及其实际作用也需要实验和相关研究比较后才能判断。

## 5. 第三步：分开记录攻击效果与成本

**先确定要回答的问题，再选择指标；所有方法使用同一套规则。**

| 指标 | 大白话解释 | 分母 |
|---|---|---|
| `flip` | 原本答对，攻击后变成非空错误回答 | 该模型共同的原本答对题数 |
| `ASR` | 回答中出现指定错误答案 | HotpotQA 全部 60 题；MuSiQue 全部 59 题 |
| 补充的定向改错比例 | 原本答对，攻击后被判错，且回答出现指定错误答案 | 同一批原本答对题数 |
| `collapse` | 原本答对，攻击后变为空答案或运行失败 | 单独报告数量，需要比例时明确分母 |
| 实际写入覆盖 | 多少道题至少有一条毒文本写入 | 全部题目 |
| 实际写入数量和长度 | 一共写了多少条、多长 | 报总量和每题分布 |
| 调用成本 | 生成与试答一共花了多少次调用、多少输入输出 token | 按题、按整次运行分别报告 |

当前的定向改错补充分析仍使用现有文字匹配规则，不能自动当作人工确认的最终答案正确性。

`n_targets_fired` 当前实际按“是否有毒文本写入”计数；要研究触发条件是否满足，应额外记录，不能只读这个数字。

### 共同分母必须明确

| 答题模型 | 现有 HotpotQA 主表原本答对题数 | 现有 MuSiQue 主表原本答对题数 |
|---|---:|---:|
| xlam-2-8b | 27 | 7 |
| qwen3-8b | 31 | 9 |
| gpt-oss-20b | 38 | 21 |
| llama-3.1-8b | 25 | 10 |

这些是当前主表的数量；每组新比较还要保存具体题目编号。数量相同，不代表是同一批题。

部分旧文件保留旧一轮的攻击前答案。比较时不能直接混用旧总数；应按选定的共同攻击前答案逐题重新计算。

### 评分需要补查

目前“包含正确答案就算对”有误判风险。例如 `Ethnomusicology` 包含 `Musicology`，可能同时命中错误与正确答案。回答重述题目后给出错误结论，也可能因为含有正确答案而被算对。

保留现有评分以便与旧实验对应；如增加只检查最终答案或人工判断的结果，要为所有方法一起计算。人工判断时尽量隐藏方法名称，并按事先写好的标准处理正误并存、拒答、空答案等情况。

## 6. 第四步：分开练习题与最终检查题

**方法需要在没参与调整的新问题上保持效果，才能说明提升有一定普遍性。**

- 另选开发题，用于调整生成方式、挑选规则和检查次数。开发题及指定错误答案事先保存，各方法共用。
- 原来的 HotpotQA 60 题、MuSiQue 59 题继续保留，用来与旧结果对应，不修改原清单。
- 原清单的结果已经被反复查看，不能再把它们称作完全没有参与方法设计的最终检查。
- 增加一批没有参与修改的新题，事先确定抽样规则和指定错误答案；新增问题及答案的准备过程单独记录，所有方法共用，不能由某个攻击方法运行时自行生成。
- 新清单需要单独的读入与覆盖检查，不应冒用现有 `--use-shared-targets` 来代表新增问题。

先用 xlam 和 gpt-oss 做开发题上的小试，验证流程，再扩展到四个模型和两个数据集。重复若干次独立生成，报告每次结果、平均表现和变化范围；重复次数在正式比较前确定，不能只留最好的一次。

## 7. 推荐的执行顺序

1. 用现有核对脚本确认当前结果可复算，检查共同攻击前答案来源。
2. 完成失败分析，补存实际搜索返回内容，检查评分容易出错的题。
3. 保存开发题和候选文本，实现 A/B 共用候选的比较。
4. 实现 C、D 的试答记录与预算限制；这些目前是设计，不是已有命令参数。
5. 在开发题上运行四组，检查试答成绩与最终攻击成绩是否一致。
6. 选定方法和设置，再与最强基线比较，同时报告写入与调用成本。
7. 在未参与调整的新题上检查，并扩展到四模型、双数据集。
8. 如果论文继续主打共享系统漏洞，再补跨用户、停用组件后残留、防护效果的专门实验；这些不能由文本成功率表替代。

## 8. 每次运行结束后需要留下什么

每题至少保存：问题编号、候选文本、候选风格、试答输入与回答、挑选依据、最终写入清单、实际搜索返回内容、攻击后回答、调用次数和异常记录。

每组至少保存：使用的模型、题目清单、共同攻击前答案来源、完整设置、运行时间，以及评分与代码版本。新结果按独立运行目录保存，不能手工修改旧结果 JSON。

## 9. 结果出来后可以支持哪些说法

| 观察到的结果 | 可以支持的解释 | 仍然需要注意 |
|---|---|---|
| 相同写入与调用预算下，C/D 在新题和重复运行中领先 | 根据实际试答挑选具有额外价值 | 报告领先和落后的全部模型、数据集 |
| 只在允许查询被攻击模型时领先 | 查询反馈有帮助 | 不能直接说对未知模型也更强 |
| 开发题领先，新题没有提升 | 方法可能过度适应开发题 | 继续保留新题失败结果 |
| 正式成功率相近，但写入或调用成本更低 | 方法有成本优势 | 成本必须完整计入生成和试答 |
| 简单近重复文本一直更强 | 原先强调的多风格解释证据不足 | 可以研究这个发现，不能只保留有利结果 |
